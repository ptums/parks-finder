## 1. Goal

A small, polished, accessible web app that helps residents find parks: see them on a map, browse a list, and open details, with optional AI-powered search. Built through a multi-agent SDLC pipeline in about 2 hours.

The brief: _"A modest app that works and is well explained is more useful than an ambitious app with broken core features."_ Slides and extra features are explicitly not required.

## 1b. Non-negotiables and negotiables

**Non-negotiable (never cut, never deferred, never "fix later"):**

1. **Accessibility.** The target is full conformance with **WCAG 2.2 Level AA**, the testable standard behind ADA web-accessibility expectations, for every view and state. Be precise about what that means: the ADA itself has no technical checklist, and automated tools catch only a fraction of real problems. So "complete" here means every applicable WCAG 2.2 A/AA success criterion is met and has a named test or a documented manual check (FR-16), AND a real screen-reader walkthrough is done by a human (FR-17). The README states the standard targeted, what was tested, and known gaps. It must **not** claim legal ADA certification or "fully compliant" without that evidence.
2. **Testing.** Every ticket ships tests; coverage thresholds are enforced; the same checks run in git hooks and CI (FR-18, FR-19).

**Negotiable (cut first when time is short):** smooth interactions and transitions: animations, easing, map fly-to, hover polish. Anything that remains must respect `prefers-reduced-motion` and must never obscure or move focus unexpectedly.

## 3. Data handling (`db/parks.sample.json`)

`db/` is a plain folder holding the JSON; there is no database server.
The brief says the sample _includes missing or empty values_, "fields may be missing or null, and arrays may be empty", and image URLs are placeholders ("placeholder images are fine"). The schema and data may be extended; any change must be described in the README ("Dataset changes").
Fields: `id`, `name`, `description`, `location{lat,lng,address}`, `amenities[]` (slugs like `dog-run`), `hours` (free-text string), `images[]` (URLs), `acreage`, `rating`.

| Field                    | Rule                                                                                                                                                           |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| any optional field       | Missing, `null`, empty string, or empty array => treated as "not provided".                                                                                    |
| `name`, `id`, `location` | The only fields a park may not lack to be usable. A record without `id`/`name` is reported by `validate:data`, and skipped by the app with a console warning.  |
| `amenities`              | Display as human labels ("dog-run" -> "Dog run"). Unknown slugs still display, humanized.                                                                      |
| `hours`                  | Verbatim free text. Never parsed, reformatted, or "open now" computed.                                                                                         |
| `images`                 | URLs may be placeholders or fail. On error show a labeled placeholder. Never hotlink-fix or invent images. Alt text: park name + "photo".                      |
| `rating`, `acreage`      | Show only when numeric. No stars-as-only-signal; include the number.                                                                                           |
| contacts                 | There is no contact field in the data. The wireframe has a Contacts block: show "Contact information not listed" (or omit the section). Don't invent contacts. |
| `location.address`       | May be a neighborhood-level string; display as-is.                                                                                                             |

The Orchestrator profiles the file in Phase 1 (`docs/DATA_PROFILE.md`) and reports surprises at G1.

## 4. UI layout [H] (from the wireframe; single page)

- **Header**: logo/title as `h1` (top-left); the search input and filters (standard by default); when AI is available, the mode radio group (Filters / AI / Both) and the AI search input; optional location button; **Reset** (clears search, filters, selection, and AI state).
- **Directory panel** (left, collapsible): "Park directory" (`h2`), a park filter input, the list.
- **Map** (main area): marker per park.
- **Park details** (opened from marker or list; popup/dialog per architect): close button (top-right), image, name (`h2`), description (`p`), amenities (`ul`), address (`h3`), hours (`h3`), contacts (`h3`).
- States to design: loading, empty/no results, AI warming up, AI unavailable, image failed, details for a sparse park.
- Phone: directory collapsed by default; details usable as a bottom sheet or dialog.

## 8. Non-functional

- **NFR-1 Accessibility (non-negotiable)**: WCAG 2.2 AA conformance per FR-16 and FR-17; targets >= 44px (above the 24px minimum); works at 200% zoom and 320px reflow; `prefers-reduced-motion` respected; usable in forced-colors / high-contrast mode (spot check).
- **NFR-2 Resilience**: any of {AI service, analytics, geolocation, images, tiles} failing must not break the core experience.
- **NFR-3 Privacy**: see FR-32; location stays in the browser.
- **NFR-4 Performance**: first load usable without waiting on the AI service or model; list/filter feel instant.
- **NFR-5 Cost safety**: rate limits, token caps, query caps, an optional daily request cap (`AI_DAILY_REQUEST_CAP`) on the public deployment, and a cheap default model (`ANTHROPIC_MODEL`). When the cap is hit, the UI says so and the standard search/filters keep working.
- **NFR-6 Quality gates (non-negotiable)**: `npm run check` (prettier check, eslint, typecheck, Jest with coverage thresholds, build) green; Husky hooks local; CI mirrors them and runs Playwright + axe; every PR has tests.
- **NFR-7 Polish (negotiable)**: smooth interactions and transitions are nice to have and are the first things cut. They never compromise NFR-1.

## 9. Out of scope (say so in the README)

Slides and a video (the brief says slides aren't needed; they're optional extras from `docs/WALKTHROUGH.md`), accounts, a database, user-generated content, parsing hours, "open now", conversation memory, a vector database, rerankers, offline/PWA, i18n, map clustering (unless trivial).
